# Multiple languages

Four stages. Each one is reachable from the previous **without a rewrite** — but
only if stage 0 was done properly. Almost all the pain in this area comes from
skipping stage 0, then discovering at stage 1 that copy is scattered across two
hundred components.

Pick the stage you are actually at, not the one you might reach.

| Stage | When | Copy lives in | How quality is assured |
| --- | --- | --- | --- |
| **0** | one language | `content.ts` next to the feature | — |
| **1** | 2–3 languages, stable set | `messages/<locale>.json` | you can still read every locale yourself |
| **2** | 4–12 languages | one table with context, generated into JSON | you cannot — gates and native-speaker review |
| **3** | many, open-ended, or non-developers editing copy | database | a status workflow: draft → reviewed → published |

**Machine translation is assumed from stage 1 onward.** Nobody hand-translates
two languages any more, and pretending otherwise produces a document that
describes a workflow no one follows. What actually changes between stages is not
*who* translates — it is **where the copy lives** and **what catches a bad
translation**, which is a real problem the moment a machine writes into a locale
you do not read.

Write the ADR before moving between stages. Each move is cheap to make and
expensive to undo.

---

## Stage 0 — one language

**This is not "no i18n".** It is the one decision that determines whether stage 1
is an afternoon or a month.

- **All user-facing copy lives in `content.ts`**, never inline in JSX. This is
  already a rule in [`AGENTS.md`](../AGENTS.md) — this is what it is for.
- **Do not install an i18n library.** You do not need one, and the wrong
  abstraction chosen now is harder to remove than to add later.
- **Do not concatenate sentences.** `"Deleted " + n + " items"` cannot be
  translated into a language with different plural rules or word order. Write
  the whole sentence per case, even in one language — see § Plurals.

```
features/greeting/
  content.ts        ← every string the feature shows
  Greeting.tsx
```

## Stage 1 — two or three languages

Files. `next-intl`, one JSON per locale, a `[locale]` route segment.

```
i18n/
  routing.ts        locales, default, prefix strategy
  request.ts        loads messages for the active locale
  navigation.ts     locale-aware Link / useRouter
messages/
  en.json           ← the source language
  de.json
app/[locale]/…      routes
```

**Key by identity, never by English text.** `nav.contact`, not
`"Contact us"`. If the key *is* the English string, rewording the English
orphans every translation silently.

### You are machine-translating, so two gates already apply

Write the source locale by hand, generate the rest. That is fine — and it means
bad data can enter a file you will not proofread line by line.

**Key parity.** A key added to one file and not the other does not crash: the
library renders the raw key, and it ships. Walk both files, compare full key
paths, fail on any key present in one and missing in the other.

**Diacritics and mojibake.** Machine output and any CSV or spreadsheet round-trip
produce ASCII fallbacks — `ae` for `ä`, `ue` for `ü`, `ss` for `ß`, unaccented
Italian vowels — and the replacement character `U+FFFD` (`�`). These read as a
font or encoding bug and are actually bad data sitting in your repository. Keep a
per-language replacement table, normalise after every generation, and fail the
build on anything left. Do not defer this to stage 2: it is needed the moment a
machine writes a locale, which at two languages is day one.

A third check earns its place as soon as you add a locale you cannot read at all:
**flag translations identical to the source.** A value that came back unchanged is
usually a failed call, not a word that happens to be the same in both languages.

### Context has nowhere to live in JSON — this is the real cost of stage 1

`{"upload.save": "Save"}` gives a translation engine one word and no situation.
Is it a button or a report heading? Imperative or noun? The engine guesses, and
at two locales you will catch it because you read both.

At the point where you stop reading every locale, that guess ships. Two options,
and picking one is the whole stage 1 → 2 decision:

- **A context sidecar** — `messages/_context.json`, same key paths, one line of
  situation per key. Keeps JSON authoring, adds a second file to keep in sync
  (so it needs its own parity check).
- **Move to stage 2 early.** If you already know a third and fourth language are
  coming, the table is less work than the sidecar plus the discipline.

Do not just skip context and hope. It is the single largest quality lever in the
whole pipeline, and its absence is invisible until a native speaker complains.

### Native language names are never translated

The language switcher shows `English`, `Deutsch`, `Italiano` — always in their
own language. Someone who cannot read the current locale still has to find their
own. This is the one string that must never go through `t()`.

## Stage 2 — up to about a dozen languages

Two things break at once, and neither is the translating.

**JSON stops working as an authoring surface** long before it stops working as a
runtime format. At six locales a copy change is a six-file diff nobody can read,
and there is nowhere structural to put context.

**You stop being able to check the output.** At two languages you catch a bad
translation because you read both. At ten you do not, so quality has to come from
structure instead of from noticing.

**Move authoring into one flat table; keep JSON as build output.**

```
i18n/workbench.csv     key | context | en | de | it | …   ← the source of truth
messages/*.json        generated — never edited by hand
```

One row per key, one column per locale. Regenerate the JSON on every change and
commit both, so the diff a reviewer reads is one row wide — and every locale for
one key sits on that row, side by side, which is the only view in which "this one
looks wrong" is a thing a person can notice.

### The `context` column is why the table exists

This is the whole reason to leave JSON, and the largest quality lever in the
pipeline. `Save` is a verb on a button and a noun in a report. `Open` is an
adjective in one place and an imperative in another. An engine given only the
word gets it wrong perhaps a third of the time.

| key | context | en |
| --- | --- | --- |
| `upload.save` | Button that commits the upload. Imperative verb. | Save |
| `filter.open` | Adjective describing a job's status. | Open |

Context makes machine output a usable draft. Without it, it is noise that costs
more to review than to write from scratch — and at ten locales nobody is
reviewing it anyway.

### The pipeline

```
export → translate → normalise → validate → import → verify
```

`normalise` and `validate` are the diacritics and mojibake steps from stage 1;
they do not change, they just now cover locales nobody on the team reads. The
same applies to flagging values identical to the source.

What is new at this stage is that **the gates are the only thing standing between
a machine and production**, so treat a failure as a blocker rather than a hint.
If a locale cannot pass, ship without that locale — a missing language falls back
to the source and is merely incomplete. A wrong one is a wrong statement made in
your product's voice.

### Gate: no hardcoded literals

Scan components for user-visible text that never went through `t()`. This is the
gate that keeps stages 1–3 honest — without it, every new feature quietly adds
English strings that no translation pipeline knows about, and the product
degrades one component at a time.

## Stage 3 — many languages, or copy that non-developers edit

Move the text into the database. Two tables:

```sql
app_texts            id, key, source_text, source_lang, context, …
app_text_translations id, app_text_id, lang, translated_text, status, …
                     status ∈ (draft, reviewed, published)
```

**`context` travels with the source text**, exactly as in stage 2 — it is what
makes both machine translation and human review possible at this scale.

**The status column is the review workflow.** Machine or on-premise translation
writes `draft`. A reviewer promotes to `reviewed`, then `published`. The app
reads only `published`, falling back to the source language. A locale can
therefore be half-finished in production without ever showing a wrong string.

### Make the language list data, not schema

```sql
-- ✗ adding a language now needs a migration that drops and re-adds a constraint
lang text not null check (lang in ('en', 'de'))

-- ✓ adding a language is one INSERT
lang text not null references public.languages (code)
```

This is the single most important difference between stage 2 and stage 3. If
adding a language requires a schema migration, you do not have open-ended
languages — you have stage 2 with extra steps. It is also the mistake that is
easiest to make and most annoying to undo, because the constraint looks like
good practice right up until the fifth locale.

### Serve it without a query per string

Reading translations per render is a performance and availability problem, and
it couples every page to the database. Snapshot instead: export published
translations to JSON at build or on a cache invalidation, and serve from that.
The database is the authoring and review surface; the runtime still reads files.

### It is a data layer, so the rules apply

Everything in [`BACKEND.md`](BACKEND.md) holds: translations are
**Sensitive**-class work, access control is enforced at the data layer (only
admins write), and the SDK sits behind an adapter. If translations are scoped
per tenant, the scope filter is not the caller's job to remember.

## Rules that hold at every stage

**Never build a sentence from parts.** Word order differs per language, so
concatenation produces text that is grammatical only in English.

```tsx
// ✗ untranslatable
`Deleted ${n} items`

// ✓ ICU, one message, plural rules per locale
t("items.deleted", { count: n })
// en: "{count, plural, one {# item} other {# items}} deleted"
// de: "{count, plural, one {# Element} other {# Elemente}} gelöscht"
```

Polish has three plural forms and Arabic six. `n === 1 ? "item" : "items"` is an
English rule hardcoded into shared code.

**Dates, numbers and currency go through `Intl`**, with the active locale — never
a hand-rolled format. `Intl.DateTimeFormat`, `Intl.NumberFormat`,
`Intl.RelativeTimeFormat` are built in and already know what you are about to get
wrong.

**Keep an English fallback at the call site.** `t("upload.save", "Save")` means a
missing translation degrades to readable English rather than a raw key on screen,
and it keeps the canonical source text next to the code that uses it.

**Design for text expansion.** German runs 30–40% longer than English, and
Finnish more. Layouts must survive it: no fixed-width buttons around a label, no
single-line assumptions. Test with the longest locale, not the shortest.

**If a target language is right-to-left** (Arabic, Hebrew, Farsi), decide before
building the layout, not after. Set `dir` on `<html>` and use logical properties
(`ms-*`/`me-*`, `start`/`end`) instead of `ml-*`/`mr-*` throughout. Retrofitting
this across an existing design system is a genuinely large piece of work.

**Every locale is in the glossary.** A domain term with two accepted translations
becomes two concepts in the user's head — [`GLOSSARY.md`](GLOSSARY.md) applies per
language, not just to English.
