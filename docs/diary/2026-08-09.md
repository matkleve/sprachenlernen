# 2026-08-09 — The method catalogue exists as data

Continues [`2026-08-08.md`](2026-08-08.md), which ends with the catalogue named
as the one unblocked piece of work everything else was waiting on. It is now
written. Change class: **Standard** — spec first, one new module, twenty-four
tests against the acceptance criteria.

| Code | `lib/method-catalogue.ts` — schema, validation, context filtering. Framework-free, no I/O |

## Decisions

- **`requires` is mandatory on a method, enforced by the validator.** Chose
  refusal over a default of "matches everything", because the default fails
  invisibly: the menu still renders, still looks plausible, and the context
  filter the whole ordering rests on has silently stopped separating anything.
  Chapter 21 already said a method without requirements cannot be admitted; it
  is now a test rather than a sentence.
- **A commitment may not carry a duration, intensity, floor or context.** Same
  reasoning from the other side. A commitment with a duration is a session, it
  reaches the daily menu, and it picks up the completion tracking A1 forbids.
  Rules out expressing "write to one friend in Italian" as a zero-minute method.
- **Time is computed from `durations`, not declared in `requires`.** Rules out
  a `time` requirement field, which would have been the same fact written
  fifty-three times and free to drift in each one. `durations: null` means
  open-ended and fits only an open block.
- **No readiness input, deliberately.** The module takes a context and nothing
  else. Chapter 26 says readiness demotes and annotates but never removes;
  accepting it here as a second filter argument is precisely how "cannot
  comply" becomes "may not", so the parameter does not exist to be misused.
- **Authored fields are named in the spec rather than smuggled.** `intensity`,
  `durations`, `doesNotDo`, `targetSignal`, `hosted` and `reviewAfterDays` are
  not derivable from the study and are all needed before a card renders. They
  live in the data files so that disagreeing with one is an edit.

## Three reconciliations between chapters, made explicitly

Writing the catalogue out forced three conflicts that reading the chapters
separately had not:

1. **Free production** carries a floor in chapter 12 and does not appear in
   chapter 21's tables at all. Added to *Writing*; chapter 06 treats it as a
   method and a floor presupposes one.
2. **The dictation floor** (1× / 10 days) attaches to full dictation on paper,
   which is what chapter 07 describes. Partial dictation carries none — chapter
   12 names "Dictation" once and there are two.
3. **Switch your phone's language**, **label the flat** and **pursue a hobby**
   are methods in chapter 21 and meet chapter 24's definition of a commitment.
   They are commitments and appear once. This is chapter 24's own correction
   being applied rather than a new judgement.

## The adversarial review, and the three things it caught

Run with fresh context against the commit, by a different agent than the one
that wrote it. It found three blocking defects, and the first is the one worth
remembering.

**A test that could not fail.** AC-18 claimed to cover the time-budget filter.
Replacing the budget comparison in `fitsTime` with `true` left all 24 tests
passing. Both of its assertions held for other reasons: the method it expected
to be present was present anyway, and the method it expected to be absent was
absent because of its writing surface. The rule the test named was the one
thing it did not check. Fixed by varying **only** the budget on one context —
and confirmed by re-running the mutation, which now fails exactly one test.

**An evidence grade with no source.** Free production has no row in chapter 21,
so its grade came from nowhere and I had written **A** while the spec listed
`evidence` among the *transcribed* fields. Grade is normative for menu ranking
until an effect estimate exists, so an invented A would have ranked the one
sourceless entry above fifty-two sourced ones. Now **B**, from chapter 06's
mark, and named in the provenance file as authored.

**A contradiction resolved silently instead of raised.** Chapter 21 gives
cooking from a recipe the context "kitchen" and defines the kitchen preset as
eyes and hands gone. Reading a recipe needs eyes. I had picked a side, which
made the one entry the chapter places in the kitchen the one entry the kitchen
cannot offer — and said nothing. That is precisely what boundary 8 is for. Now a
⚠ SPEC GAP and a pinned test.

Also fixed: the SRS session is "touch **or** voice" in chapter 21, which one
requirement set cannot express, so the only method with a daily floor was
unofferable in four of seven presets. `requires` now takes alternative sets.
Background listening was `D` where the chapter says "C, weak" — the worst entry
in the catalogue to shift by hand, since it is the chapter's own test of whether
weak methods are included honestly. And the eyes-free test used reading aloud,
whose eyes requirement I had authored, so it was asserting my own value while
appearing to assert the chapter's.

The reviewer confirmed transcription coverage is complete — 55 rows, minus three
documented moves, plus free production, is 53 — and that the five floors are
exact.

**What generalises.** Two of the three blocking findings are the same failure:
a test or a spec line that *names* a rule while resting on something else. The
mutation check is what separated them from the twenty-one tests that were fine,
and it took one command. Worth doing on any test whose assertion could pass for
a second reason.

## Second pass — the key names, and a queue holding work that was already done

User question, and it was the right one to ask: `.env.example` says *anon key* —
does Supabase's own documentation still say that? It does not. Publishable
(`sb_publishable_…`) and secret (`sb_secret_…`) replaced the `anon` /
`service_role` JWT pair, which Supabase now labels legacy and deprecates at the
end of 2026. The file an implementer copies **from** was a generation behind the
dashboard they copy **into**, and the user had already done the right thing by
pasting a publishable key the example file did not mention.

The elevated key keeps its `SUPABASE_SERVICE_ROLE_KEY` name on purpose, and the
reason is written next to it: renaming a variable ahead of rotating the key it
names takes the credential away from the running deployment. The tidy-looking
edit is the wrong one, so the note exists to stop the next reader making it.

[ADR-0007](../adr/0007-supabase-as-the-provider.md) still says "anon key" in its
consequences and was left alone. An ADR records what was decided when it was
decided; this repo's rule is to supersede a record, never to edit it into
consistency. `.env.example` is the live document and it is now correct.

### The conflict the resync exposed

Reading ADR-0009 against the plan turned up two accepted records that cannot both
hold. ADR-0009's consequences: *"Methods is the default route. `/` is the menu,
not a dashboard."* The plan, in two places, from ADR-0006 and the 2026-08-08
instruction: *`/` is the landing page, and the app is not on it.*

The reconciliation everyone reaches for — `/` is the public landing page and
Methods is the default route of the *signed-in* app — is written down nowhere.
It is precisely the plausible guess boundary 8 exists to stop, and a guessed rule
that happens to be right is still a decision nobody made. It blocks T-B10, since
a menu spec cannot say where the menu lives, and it blocks T-04, which writes a
holding page onto the same route.

Worth recording how it was found: not by a gate. `check:specs` verifies that
links resolve, not that two documents agree. It surfaced from reading one ADR
while editing the file it had invalidated. The nineteenth pass on 2026-08-08 made
the same observation about a normative sentence with three owners — this is the
same failure one level up, a **route** with two owners.

## Third pass — the first screen that belongs to this product

### The test that carries the feature

One test matters more than the other fourteen: a profile carrying a hand-written
`qualityTier: "A"` next to a null lemma table must still render **C**. That is
UC-036's whole thesis — *a tier someone can set by hand is not a quality
statement* — and it is the one property that fails silently, because a page
showing a reassuring letter looks exactly like a page showing a derived one.

Mutation-checked rather than trusted: replacing the derivation with
`profile.qualityTier ?? qualityTier(profile)` fails **exactly that test and no
other**. That is the check the seventh and fifteenth passes both arrived at from
different directions, and it took one command.

### Decisions

- **A refused profile is listed by file name with its errors, never skipped.** A
  language that failed to load and a language nobody has added look identical
  once you drop one in silence, and the page whose subject is trust is the worst
  place to have an invisible failure mode.
- **The I/O lives in `features/language-status/profiles.ts`.** Not `lib/`, which
  is I/O-free by construction and whose loaders take parsed input on purpose;
  not `app/`, because logic in a `page.tsx` is logic no test can reach without a
  router. The directory read takes a `root` parameter so the test can point it at
  a fixture, which is also what made the malformed-profile path testable at all.
- **The per-tier sentences render `lexicon.md`'s tier table; they do not restate
  it.** One owner per normative rule. If what tier B claims ever changes, it
  changes in the service spec and this page follows — the reverse would put the
  same sentence in two files and let them drift, which is the failure the
  fifteenth pass caught between chapter 18 and the spec.
- **No badge, no colour-only tier.** The letter is text in its own cell, because
  the difference between B and C has to survive being read aloud.

### Went wrong — an acceptance criterion that contradicted the page

The first draft of the criteria said *"given no valid profile, the empty line
renders and no table does"*. Then the refused-profile decision added a second
table, which can be on screen precisely when there are no valid profiles. The
criterion and the page would have disagreed on their first real input.

Caught while implementing rather than by a gate, which is the ordinary way this
gets caught and an argument for implementing against your own criteria before
believing them. Fixed by narrowing the sentence to *no **language** table* and
saying in `## States` that the refused list is not one of the two states. Worth
noting the shape: the defect was not in either decision, it was in an "and no X"
written before X was plural.

`success-deep`, answering the other question with the conventional answer:

### T-04, and the home route finally changes hands

The demo is at `/primitives`, `/` carries one sentence quoted verbatim from
thesis 1 and a link to `/languages`, and the root layout stopped titling every
page "Grundriss". `/` went from 3.72 kB of client JS to 164 B.

The link is a styled anchor, not a `Button` — it navigates, so it has to survive

`Gap: no Link primitive.` Creating one is a Standard change with its own spec,
and T-04 is Trivial; the second surface that needs it is where it earns that.

### Went wrong — nine bytes of CSS, and two reviewers who were right

The walkthrough recording came back from review with the app apparently broken:
buttons colliding, bullet points on styled lists, no spacing, `hover:` doing
nothing, and an item picker that would not respond to a click. My first instinct
was that the reviewer had misread a compressed video. It had not.

`/_next/static/css/app/layout.css` was **9 bytes**, and the nine bytes were the
string `Not Found`. Running `npm run verify` while `npm run dev` was live had
let `next build` overwrite the manifests the dev server was still serving from.
The source was never wrong — the production CSS from the same commit is 26 kB
and correct, which is precisely why `verify` stayed green through all of it.

Two things worth keeping. **The tell was the disagreement itself**: a green
production build cannot coexist with globally missing CSS, so when the gate and
the browser disagree at that scale, the server is the suspect and not the
source. And the existing trap *"the dev server serves the last build"* tells you
to rebuild before screenshotting — which, with `dev` running, is the instruction
that causes this. Both are now in [`../TRAPS.md`](../TRAPS.md), adjacent, with
the second naming the first.

This is the exact thing `AGENTS.md` means by *automated gates do not prove
browser behavior*. Seven green `verify` runs and one screenshot had all passed
over an app that was serving no stylesheet at all.

### One thing not fixed, because fixing it is a design decision

Both the video reviewer and the browser agent reported no visible hover change
on the home link, twice, and after the CSS was restored. The rule is present and
correct in the served stylesheet — `.hover\:text-accent-deep:hover { color:
var(--color-accent-deep) }` — and the delta is `#2f5ad0` → `#2445a4`, which is
the design system's own accent hover, the same one `Button` uses.

So the state exists and two observers could not see it. That is a statement
about the palette rather than about this link, and making a text link's hover
more visible is a visual change nobody asked for (boundary 6). Recorded as an
open question instead.

# 2026-08-09 — Accounts and authentication on Supabase (T-B8)

Second entry today, separate area. Change class: **Sensitive** — spec first,
red-test-first, fresh-context adversarial review.

## Shipped

| Area | What |
| --- | --- |
| Spec | `docs/specs/service/auth.md`, traced to UC-011, ADR-0006, ADR-0007 |
| DB | `supabase/migrations/20260809073100_review_log_ownership.sql` — `review_log` table, RLS `select`/`insert` policies scoped to `auth.uid() = user_id`, `to authenticated` only, no `update`/`delete` grant or policy for any role |
| Code | `lib/db/client.ts` (browser/server Supabase factories via `@supabase/ssr`), `lib/db/auth.ts` (`signUp`/`signIn`/`signOut`/`getAccount`), `middleware.ts` (session refresh) |
| UI | `features/auth/` (`SignUpForm`, `SignInForm`, `actions.ts`, `content.ts`) and `app/signup/`, `app/login/` — built only from `Field` and `Button`, no new component |
| Tests | `lib/db/auth.test.ts` (9 tests, offline, outcome mapping); `lib/db/access-control.test.ts` (5 tests, BACKEND.md §8 policy test, against the live project) |
| Docs | `docs/GLOSSARY.md` — added **Account** and **Auth session**, the latter because bare "Session" already means a fixed-length run of Tasks |

`npm run verify`: typecheck, lint, specs, tokens, contrast and build all green.
`test` is red — see below, deliberately.

## Decisions

- **`lib/db/client.ts` and `middleware.ts` are the only two files allowed to
  import `@supabase/ssr` outside this spec's own tests.** Everything else —
  `auth.ts`, the actions, the pages — goes through `lib/db/client.ts` or
  through `lib/db/auth.ts`'s exported functions. `middleware.ts` is a
  necessary second seam, not a slip: it runs before any Server Component and
  needs the request/response cookie API, which only `@supabase/ssr`'s
  middleware pattern provides. (Caught by the adversarial review — the first
  pass claimed a single seam and `middleware.ts` contradicted it on inspection.)
- **`signUp`/`signIn`/`signOut` return discriminated unions, never throw.** A
  Supabase error is data the caller must branch on (`{ status: "error", error }`),
  not an exception the page has to remember to catch. Matches
  `CONSTITUTION.md`'s "no silent failure" from the other direction — the failure
  is loud but typed, not an unhandled rejection.
- **`access-control.test.ts` talks to the real project, not a mock.** The thing
  under test is a database policy; a mocked Supabase client would only prove the
  mock was called (`docs/TRAPS.md`'s "test that cannot fail"). It
  `describe.skipIf`s, visibly, when the three secrets are absent, rather than
  failing every environment that has not configured them.
- **No `update`/`delete` grant at all, not just no policy.** Verified locally
  against a throwaway Postgres before trusting it: with the grant present and
  only RLS denying it, an `update`/`delete` against another user's row returns
  zero rows affected, same as with no grant — so the extra layer is redundant
  today, but it is the actual enforcement of "append-only" (ADR-0005) rather
  than a policy nobody's query has broken yet. Recorded in both the migration's
  comments and the test's, since a future reader could mistake it for defensive
  overkill.
- **`Auth session` is a new glossary term, not `Session`.** `Session` already
  means a fixed-length run of Tasks (`docs/GLOSSARY.md`). Reusing it for
  Supabase's signed-in cookie state would collide the moment a spec needs both
  in the same sentence, which `auth.md` §States does.

## Went wrong, then resolved the same day

- **No DDL credentials were available to apply the migration to the live
  project.** The three secrets set at the time (`NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) only ever
  reach PostgREST and the Auth API — none of them opens a Postgres connection or
  the Management API, which is what running a migration needs. Confirmed by
  running `access-control.test.ts` against the live project: it failed with
  `PGRST205` ("Could not find the table 'public.review_log'"), the correct red
  state for a migration that has not been applied yet, not a bug in the RLS
  logic (verified separately against a local Postgres — see the migration's own
  comments).
- **Resolved once `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD` were
  added.** `npx supabase link --project-ref lnkgmjcueahhrzpnzmwq` followed by
  `npx supabase db push` applied `20260809073100` to the live project;
  `supabase migration list` then reports it local **and** remote. `npm test --
  access-control` went from three failures to five passes with no code change —
  which is the evidence that the red was the environment, not the policy.

**The lesson, which generalises past this task.** The keys the *app* needs and
the keys a *migration* needs are disjoint sets, and nothing in the app's own
`.env` tells you that. A task whose Definition of Done includes a schema change
is not ready to hand out unless `SUPABASE_ACCESS_TOKEN` and
`SUPABASE_DB_PASSWORD` are in the executing environment — otherwise the agent
does all the work correctly and still cannot finish, exactly as happened here.
Both are now documented in `.env.example` under a heading that says
"migrations only, never read by the app".

## Open

- **⚠ SPEC GAP, `docs/specs/service/auth.md` § Open questions:** the Supabase
  project currently requires email confirmation before a session exists, which
  sits in tension with UC-011's "first real exercise reachable in well under a
  minute." `signUp` handles both outcomes correctly either way; whether the
  product should turn confirmation off is a decision for whoever owns UC-011.
  Still open — the credential that arrived unblocks migrations, not product
  decisions.
- T-B2 (persistence of the review row's own payload) is now fully unblocked:
  `user_id` exists in the live schema, so its red test can run for real.

| Cleanup | T-01 (Dialog's description and its id), T-02 (the Space criterion), and `verify` stopped writing into `.next` |

## Decisions

- **The menu shipped without the learner half, on purpose.** No daily three, no
  current standing, no demonstration sentence, no readiness, no skill filter.
  Every one of them needs stored history or an effect estimate that does not
  exist, and a front door that invents them is the exact failure
  [`../study/25-why-it-does-not-feel-productive.md`](../study/25-why-it-does-not-feel-productive.md)
  spends a chapter on. What is left is honest and small: here is everything the
  app can do, here is what each thing will not do for you.
- **`lib/routes.ts` exists because the gate and the navigation must not be able
  to disagree.** A destination added to the shell and not to `protectedRoutes`
  is a public page nobody meant to publish; one list makes that unrepresentable,
  and a test asserts the set is exactly the three destinations.

## Went wrong — the auth gate that returned the page it was refusing

`app/(app)/layout.tsx` awaited an account and redirected. Nine tests passed,
including one asserting the redirect. Against a production build, `curl /methods`
signed out returned **307 with 124 kB of body**: the whole rendered method menu,
inside the redirect's flight payload. With `app/loading.tsx` above it, worse —
a **200** carrying a client-side redirect instruction, which works in a browser
and is wide open to anything that does not run JavaScript.

A layout and the page beneath it render concurrently. The redirect wins the
status, not the race. The fix is `middleware.ts`, the only layer that runs
before rendering; the layout gate stays as the backstop for a route the matcher
stops covering. Now 307 with an empty body.

**The part worth keeping is how it was found.** Not by a test — jsdom renders no
routes, so the unit test asserting `redirect("/login")` was true and useless. By
`curl -D -` against `npm run start`, reading the **body size** rather than the
status. For any gate, the question is not "did it redirect" but "what did it
send".

## Went wrong — the same nine bytes, twice

The walkthrough recording came back reporting an unstyled app: default browser
links, no pills, no cards. The fourth pass had already diagnosed this exact
symptom and written the trap. It happened again anyway, because the trap's
remedy was a rule — *do not run `verify` and `dev` at once* — and a rule is
something a person has to remember at the moment they are thinking about
something else.

So `verify` now builds into `.next-verify` (`NEXT_DIST_DIR`, read by
`next.config.ts`), and the collision is not available to make. The clean
production build serves a 27 kB stylesheet and the compiled CSS contains every
utility the components ask for; nothing in the source was ever wrong, either
time.

**A gate that can invalidate the thing you are about to inspect will be blamed
on the source, because the source is what you were already looking at.** Where
the choice exists, give the gate its own output instead of writing a rule.

## Went wrong — a third time, and the same shape as the first two

Two reviewers said the current destination was marked with "an underline". It is
a filled pill. Measured off the screenshot: the current item's background is
`rgb(230, 240, 248)` against a white header, which is `--color-accent-soft`
exactly, and the unchosen chips sit on bare canvas. Vision descriptions of
low-contrast fills are not evidence; pixels are. That took one `getPixel` call
and should have come before any code was read.

Chasing it turned up something real, though. **No hover state in this app has
ever been visible in this VM**, because Tailwind v4 puts every `hover:` utility
inside `@media (hover: hover)` and the VM's display reports `pointer: none`.
`Button`'s hover is specced, tested and equally invisible here. The fourth pass
had already met this and diagnosed it as a palette that was too subtle; that
open question is withdrawn above, and the finding is in
[`../TRAPS.md`](../TRAPS.md).

Three failures today — nine bytes of CSS, the redirect that rendered its own
page, and this — and all three have one shape: **the environment lying quietly
while the source was innocent.** The instinct each time was to go and change
code that was already correct. The defence is not more care, it is measuring the
served bytes, the response body, and the computed style before touching a file.
