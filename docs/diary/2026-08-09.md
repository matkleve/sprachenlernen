# 2026-08-09 — The method catalogue exists as data

Continues [`2026-08-08.md`](2026-08-08.md), which ends with the catalogue named
as the one unblocked piece of work everything else was waiting on. It is now
written. Change class: **Standard** — spec first, one new module, twenty-four
tests against the acceptance criteria.

## Shipped

| Area | What |
| --- | --- |
| Data | `data/methods/` — eight section files, 53 methods and 6 commitments, plus the seven context presets |
| Code | `lib/method-catalogue.ts` — schema, validation, context filtering. Framework-free, no I/O |

| Tests | `lib/method-catalogue.test.ts`, 24 tests covering AC-1 … AC-22 |

`npm run verify` green: typecheck, lint, specs, tokens, contrast, 201 tests,
build.

## Decisions

- **`requires` is mandatory on a method, enforced by the validator.** Chose
  refusal over a default of "matches everything", because the default fails
  invisibly: the menu still renders, still looks plausible, and the context
  filter the whole ordering rests on has silently stopped separating anything.
  Chapter 21 already said a method without requirements cannot be admitted; it
  is now a test rather than a sentence.
- **A commitment may not carry a duration, intensity, floor or context.** Same
  reasoning from the other side. A commitment with a duration is a session, it
  reaches the daily menu, and it picks up the completion tracking A1 forbids.
  Rules out expressing "write to one friend in Italian" as a zero-minute method.
- **Time is computed from `durations`, not declared in `requires`.** Rules out
  a `time` requirement field, which would have been the same fact written
  fifty-three times and free to drift in each one. `durations: null` means
  open-ended and fits only an open block.
- **No readiness input, deliberately.** The module takes a context and nothing
  else. Chapter 26 says readiness demotes and annotates but never removes;
  accepting it here as a second filter argument is precisely how "cannot
  comply" becomes "may not", so the parameter does not exist to be misused.
- **Authored fields are named in the spec rather than smuggled.** `intensity`,
  `durations`, `doesNotDo`, `targetSignal`, `hosted` and `reviewAfterDays` are
  not derivable from the study and are all needed before a card renders. They
  live in the data files so that disagreeing with one is an edit.

## Three reconciliations between chapters, made explicitly

Writing the catalogue out forced three conflicts that reading the chapters
separately had not:

1. **Free production** carries a floor in chapter 12 and does not appear in
   chapter 21's tables at all. Added to *Writing*; chapter 06 treats it as a
   method and a floor presupposes one.
2. **The dictation floor** (1× / 10 days) attaches to full dictation on paper,
   which is what chapter 07 describes. Partial dictation carries none — chapter
   12 names "Dictation" once and there are two.
3. **Switch your phone's language**, **label the flat** and **pursue a hobby**
   are methods in chapter 21 and meet chapter 24's definition of a commitment.
   They are commitments and appear once. This is chapter 24's own correction
   being applied rather than a new judgement.

## The adversarial review, and the three things it caught

Run with fresh context against the commit, by a different agent than the one
that wrote it. It found three blocking defects, and the first is the one worth
remembering.

**A test that could not fail.** AC-18 claimed to cover the time-budget filter.
Replacing the budget comparison in `fitsTime` with `true` left all 24 tests
passing. Both of its assertions held for other reasons: the method it expected
to be present was present anyway, and the method it expected to be absent was
absent because of its writing surface. The rule the test named was the one
thing it did not check. Fixed by varying **only** the budget on one context —
and confirmed by re-running the mutation, which now fails exactly one test.

**An evidence grade with no source.** Free production has no row in chapter 21,
so its grade came from nowhere and I had written **A** while the spec listed
`evidence` among the *transcribed* fields. Grade is normative for menu ranking
until an effect estimate exists, so an invented A would have ranked the one
sourceless entry above fifty-two sourced ones. Now **B**, from chapter 06's
mark, and named in the provenance file as authored.

**A contradiction resolved silently instead of raised.** Chapter 21 gives
cooking from a recipe the context "kitchen" and defines the kitchen preset as
eyes and hands gone. Reading a recipe needs eyes. I had picked a side, which
made the one entry the chapter places in the kitchen the one entry the kitchen
cannot offer — and said nothing. That is precisely what boundary 8 is for. Now a
⚠ SPEC GAP and a pinned test.

Also fixed: the SRS session is "touch **or** voice" in chapter 21, which one
requirement set cannot express, so the only method with a daily floor was
unofferable in four of seven presets. `requires` now takes alternative sets.
Background listening was `D` where the chapter says "C, weak" — the worst entry
in the catalogue to shift by hand, since it is the chapter's own test of whether
weak methods are included honestly. And the eyes-free test used reading aloud,
whose eyes requirement I had authored, so it was asserting my own value while
appearing to assert the chapter's.

The reviewer confirmed transcription coverage is complete — 55 rows, minus three
documented moves, plus free production, is 53 — and that the five floors are
exact.

**What generalises.** Two of the three blocking findings are the same failure:
a test or a spec line that *names* a rule while resting on something else. The
mutation check is what separated them from the twenty-one tests that were fine,
and it took one command. Worth doing on any test whose assertion could pass for
a second reason.

## Open

- **⚠ SPEC GAP: twenty-one methods have no layer-1 signal**, and neither does
  any commitment. Shadowing trains prosody, minimal pairs train perception,
  reading aloud trains intelligibility — chapter 03's seven signals cover none
  of them. Chapter 12 says a method without a named target signal cannot be
  admitted. Either the signal list is short by two or three, or that rule binds
  only hosted methods. This is the largest thing the exercise surfaced and it
  was not visible from any single chapter.
- **⚠ SPEC GAP: `intensity` is authored on a 1–3 scale with no definition.**
  Chapter 12's card requires the field and nothing defines what a 2 is. Before
  it reaches a card it needs one, or it is three shades of nothing.
- **⚠ SPEC GAP: no entry for what happens when nothing fits the context**,
  carried over from chapter 21. Every shipped preset yields something today,
  which is why it is not urgent and also why it will be found late.
- **⚠ SPEC GAP: `SKILLS` has no `vocabulary` value**, so the three vocabulary
  methods ship with an empty skill set and `bySkill` silently omits the app's
  core loop. Same shape as the signal gap: extend what a method may target, or
  narrow chapter 12's rule.
- **No preset can reach *translate a song*** — it needs a keyboard and an open
  block, and no preset has both. Pinned by a test so the list cannot grow.
- **The off-app share is 34% where thesis 9 says about half.** Either the
  catalogue is short of off-app entries or the thesis overstates.
- Presets are constants. Chapter 21 says they are editable; nothing here writes.
- Everything still open from 2026-08-08 remains open, including the readiness
  quantity (UC-064) and the navigation model (UC-063), which is now the next
  thing in the way of the menu itself.

# 2026-08-09 — Accounts and authentication on Supabase (T-B8)

Second entry today, separate area. Change class: **Sensitive** — spec first,
red-test-first, fresh-context adversarial review.

## Shipped

| Area | What |
| --- | --- |
| Spec | `docs/specs/service/auth.md`, traced to UC-011, ADR-0006, ADR-0007 |
| DB | `supabase/migrations/20260809073100_review_log_ownership.sql` — `review_log` table, RLS `select`/`insert` policies scoped to `auth.uid() = user_id`, `to authenticated` only, no `update`/`delete` grant or policy for any role |
| Code | `lib/db/client.ts` (browser/server Supabase factories via `@supabase/ssr`), `lib/db/auth.ts` (`signUp`/`signIn`/`signOut`/`getAccount`), `middleware.ts` (session refresh) |
| UI | `features/auth/` (`SignUpForm`, `SignInForm`, `actions.ts`, `content.ts`) and `app/signup/`, `app/login/` — built only from `Field` and `Button`, no new component |
| Tests | `lib/db/auth.test.ts` (9 tests, offline, outcome mapping); `lib/db/access-control.test.ts` (5 tests, BACKEND.md §8 policy test, against the live project) |
| Docs | `docs/GLOSSARY.md` — added **Account** and **Auth session**, the latter because bare "Session" already means a fixed-length run of Tasks |

`npm run verify`: typecheck, lint, specs, tokens, contrast and build all green.
`test` is red — see below, deliberately.

## Decisions

- **`lib/db/client.ts` and `middleware.ts` are the only two files allowed to
  import `@supabase/ssr` outside this spec's own tests.** Everything else —
  `auth.ts`, the actions, the pages — goes through `lib/db/client.ts` or
  through `lib/db/auth.ts`'s exported functions. `middleware.ts` is a
  necessary second seam, not a slip: it runs before any Server Component and
  needs the request/response cookie API, which only `@supabase/ssr`'s
  middleware pattern provides. (Caught by the adversarial review — the first
  pass claimed a single seam and `middleware.ts` contradicted it on inspection.)
- **`signUp`/`signIn`/`signOut` return discriminated unions, never throw.** A
  Supabase error is data the caller must branch on (`{ status: "error", error }`),
  not an exception the page has to remember to catch. Matches
  `CONSTITUTION.md`'s "no silent failure" from the other direction — the failure
  is loud but typed, not an unhandled rejection.
- **`access-control.test.ts` talks to the real project, not a mock.** The thing
  under test is a database policy; a mocked Supabase client would only prove the
  mock was called (`docs/TRAPS.md`'s "test that cannot fail"). It
  `describe.skipIf`s, visibly, when the three secrets are absent, rather than
  failing every environment that has not configured them.
- **No `update`/`delete` grant at all, not just no policy.** Verified locally
  against a throwaway Postgres before trusting it: with the grant present and
  only RLS denying it, an `update`/`delete` against another user's row returns
  zero rows affected, same as with no grant — so the extra layer is redundant
  today, but it is the actual enforcement of "append-only" (ADR-0005) rather
  than a policy nobody's query has broken yet. Recorded in both the migration's
  comments and the test's, since a future reader could mistake it for defensive
  overkill.
- **`Auth session` is a new glossary term, not `Session`.** `Session` already
  means a fixed-length run of Tasks (`docs/GLOSSARY.md`). Reusing it for
  Supabase's signed-in cookie state would collide the moment a spec needs both
  in the same sentence, which `auth.md` §States does.

## Went wrong (in progress, not yet resolved)

- **No DDL credentials were available to apply the migration to the live
  project.** The three secrets set (`NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) only ever
  reach PostgREST and the Auth API — none of them opens a Postgres connection or
  the Management API, which is what running a migration needs. The Supabase MCP
  server needs the user to authenticate it in the Cursor IDE first, which a
  cloud agent cannot do on its own. Confirmed by running
  `access-control.test.ts` against the live project: it fails with `PGRST205`
  ("Could not find the table 'public.review_log'"), the correct red state for a
  migration that has not been applied yet, not a bug in the RLS logic (verified
  separately against a local Postgres — see the migration's own comments).
- **This is the expected state for this handoff, not a stall**: the code and
  the migration file are both finished and reviewed; what is missing is a
  one-time action only a human with project access (or a stronger secret) can
  take. See `docs/IMPLEMENTATION-PLAN.md` § "Where storage stands" for the exact
  unblock steps.

## Open

- **⚠ SPEC GAP, `docs/specs/service/auth.md` § Open questions:** the Supabase
  project currently requires email confirmation before a session exists, which
  sits in tension with UC-011's "first real exercise reachable in well under a
  minute." `signUp` handles both outcomes correctly either way; whether the
  product should turn confirmation off is a decision for whoever owns UC-011,
  not something this task's author could decide or (without Management API
  access) even change.
- Apply `supabase/migrations/20260809073100_review_log_ownership.sql` to the
  live project, then `npm test -- access-control` should be the only thing that
  changes from red to green.
- T-B2 (persistence of the review row's own payload) is unblocked to start its
  spec now that `user_id` exists in the schema, but its own red test needs the
  same migration applied to run for real.
