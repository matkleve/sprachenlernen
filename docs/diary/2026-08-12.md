## Idea evaluation: same-session requeueing — "how is the feedback saved"

**Change class: Trivial (docs only).** Owner clarified the same-session
requeue idea (`docs/IDEAS.md`, 2026-08-12 entry) is Anki-style self-grading
throughout — no typed/checked answer was ever proposed, correcting my
misreading in the prior pass — and asked specifically how a same-run repeat's
outcome gets saved.

Resolved without new design: every attempt (including same-run repeats)
still writes one `review_log` row via the existing shape; "needed more tries
→ comes back sooner" is not a feature to add, it is `stabilityAfterLapse` in
`lib/scheduler.ts` already lowering `stability` on an `again`/`hard` grade,
which FSRS already turns into a shorter next interval. A flat "3 or 8 days ±
randomness regardless of tries" alternative would be a downgrade — it drops
the per-card signal FSRS was chosen for. The only genuinely new piece is the
within-run position ("back in ~5 cards"), which has no FSRS equivalent
(shortest native gap ≈0.49 days) and must live as session-local client state,
never through the scheduler. Also corrected: the earlier "two clocks confuse
trust" objection doesn't hold — no due date/backlog/badge is ever shown to
the user (`review-session.md`, `words-home.md`, `words.md`, UC-006), so there
is only one visible clock and nothing for a same-run mechanic to compete
with. Still `🆕 unevaluated` — no use case named yet, no code changed.

## Extending UC-023 for a broken-card flag; a detection formula for UC-013

**Change class: Trivial (docs only).** Owner asked for a way to flag an
obviously-broken card for review, scoped per (learning language, gloss
language); confirmed suspension/flagging must **not** remove a card
mid-session; and asked for a UX-designer's read on how to actually detect
*why* a card is broken (the *pero*/*perro* case).

- **Reuse: UC-023** (`report something the app got wrong`) already covers
  flag-and-stop-scheduling with no moderator role required — this was the
  same goal, not a new one. Added the language-pair scoping (a report is
  about one Gloss-language text on one Learning-language card, not the Word
  in the abstract — matters once UC-070 ships more than one gloss language)
  and an explicit "v1 is a flag, not a review-queue UI" out-of-scope line.
- **Mid-session disappearance — checked, not a new mechanism.** `session-builder.md`
  already builds the queue once, at `preparing`, and never revisits it —
  so a card suspended mid-run was never going to vanish from the run in
  progress; the existing fixed-queue design already gives the behaviour the
  owner wants. Documented explicitly in UC-023 so it isn't re-litigated.
- **`docs/IDEAS.md`** — new design note answering "how do we detect that": a
  three-tier model (static content-time candidates — multiple senses, no
  context, lemma similarity, sound-contrast tables; behavioural leech
  detection already shipped; a one-tap confirm at suspension time, since
  self-grading carries no content signal to auto-diagnose from). Answers
  the mechanism ADR-0004 assumed but never specified ("minimal-pair tasks
  appear only when a confusion is detected"). Two `⚠ SPEC GAP`s carried
  forward: static vs per-learner detection, and the actual similarity
  threshold. No code yet.
