## Idea evaluation: same-session requeueing — "how is the feedback saved"

**Change class: Trivial (docs only).** Owner clarified the same-session
requeue idea (`docs/IDEAS.md`, 2026-08-12 entry) is Anki-style self-grading
throughout — no typed/checked answer was ever proposed, correcting my
misreading in the prior pass — and asked specifically how a same-run repeat's
outcome gets saved.

Resolved without new design: every attempt (including same-run repeats)
still writes one `review_log` row via the existing shape; "needed more tries
→ comes back sooner" is not a feature to add, it is `stabilityAfterLapse` in
`lib/scheduler.ts` already lowering `stability` on an `again`/`hard` grade,
which FSRS already turns into a shorter next interval. A flat "3 or 8 days ±
randomness regardless of tries" alternative would be a downgrade — it drops
the per-card signal FSRS was chosen for. The only genuinely new piece is the
within-run position ("back in ~5 cards"), which has no FSRS equivalent
(shortest native gap ≈0.49 days) and must live as session-local client state,
never through the scheduler. Also corrected: the earlier "two clocks confuse
trust" objection doesn't hold — no due date/backlog/badge is ever shown to
the user (`review-session.md`, `words-home.md`, `words.md`, UC-006), so there
is only one visible clock and nothing for a same-run mechanic to compete
with. Still `🆕 unevaluated` — no use case named yet, no code changed.

obviously-broken card for review, scoped per (learning language, gloss
language); confirmed suspension/flagging must **not** remove a card

## Word identity vs. description text: two separate records, not one file

**Change class: Trivial (docs only).** Owner: dropped the word "gloss"
entirely (rightly — it was landing as a third invented language, not what it
meant), and gave the actual acceptance test in one sentence: start learning
Spanish with the setting on English, switch the setting to German, keep
learning Spanish, **same progress**. That single sentence resolves the
storage-shape question left open last turn.

- **Resolved:** the word being learned (its `taskId`, its schedule, its
  review history) and the text that describes it are **two separate
  records**, joined by (word, spoken language) at render time — never one
  file per spoken language. A duplicate-deck-per-spoken-language design is
  now explicitly **rejected** in `UC-069`, not left as an open option: it
  would risk a different `taskId` per spoken language, and switching the
  setting would look like starting over, which directly fails the owner's
  acceptance test.
- Scrubbed "gloss"/"gloss language" out of `UC-069`, `UC-023`, and
  `GLOSSARY.md` (kept only inside the "here is the mistake I made" correction
  note in `UC-069`, for the record) — replaced with plain language: "the text
  that describes a word," "description text."
- `UC-023`'s dependency on `UC-069` is **unblocked**: a report's key is
  (`wordId`, spoken language), which now exists. What's left open there is
  narrower — whether a report can point at *part* of a description, deferred
  until `UC-069`'s "one string vs. split parts" question resolves.
- Still open on `UC-069`: where non-English description text is sourced from
  (Kaikki only ships English), and the one-string-vs-parts question.
